## 1. 새니타이제이션

### 1.1 결함 탐지 복습

- 테스트는 주어진 구현에 대해 명세 위반을 탐지하며, 명세와 구현은 모두 구체적인 인스턴스이다.
- 명세는 정책에 따라 불법 연산을 정의한다.
- 테스트 케이스는 단언문, 세그먼테이션 폴트, 0으로 나누기 트랩, 처리되지 않은 예외, 종료를 유발하는 완화 기법을 통해 버그를 탐지한다.
- 핵심 아이디어는 **명세를 검증하는 검사로 코드를 보강**하는 것이다.

### 1.2 동적 테스트의 요구 조건

동적 테스트를 통한 결함 탐지에는 **두 가지 구성 요소**가 필요하다.

1. 결함을 **유발하는** 메커니즘.
2. 결함을 **탐지 가능하게** 만드는 메커니즘.

퍼징과 심볼릭 실행은 결함을 유발하는 입력을 탐색하고, 새니타이저는 실행 중 발생한 위반을 탐지한다.

### 1.3 새니타이저란

**새니타이저(sanitizer)는 주어진 정책을 강제하고, 버그를 더 일찍 탐지하며, 테스트의 효과를 높인다.** 대부분의 새니타이저는 정적 분석, 계측, 동적 분석의 조합에 의존한다.

1. 프로그램을 **컴파일 중에 분석**한다(예: 타입 그래프 같은 속성을 학습하거나 최적화를 가능하게 하기 위해).
2. 프로그램을 **계측**한다(예: 검사용 메타데이터를 기록하고 정책 검사를 실행하기 위해).
3. **런타임에** 계측 코드가 정책이 유지되는지 끊임없이 검증한다.

모든 새니타이저의 설계 질문은 다음과 같다: **어떤 정책**을 강제할 것인가, **어떤 메타데이터**를 기록할 것인가, **어디서** 검사할 것인가.

## 2. AddressSanitizer (ASan)

### 2.1 개요

AddressSanitizer는 버퍼 오버플로우와 일부 시간적 위반 등 **메모리 주소 버그**를 찾는다. 접근 가능성 맵은 각 포인터가 원래 어느 객체를 가리켰는지까지 모두 기록하지는 않는다. 레드존을 건너뛰고 다른 접근 가능한 객체에 도달하거나, 해제 영역이 새 객체로 재사용된 뒤 이전 포인터로 접근하면 탐지하지 못할 수 있다.

**구현:**

- 컴파일러 모듈(clang/gcc에서 사용 가능).
- 컴파일 시간에 로드와 스토어를 계측한다.
- 컴파일 시간에 스택과 전역 변수 주변에 레드존을 배치한다.
- 런타임 모듈이 `malloc`을 가로챈다.

사용하려면 `-fsanitize=address`로 컴파일한다(예: `gcc test.c -fsanitize=address`).

### 2.2 섀도 메모리와 레드존

ASan은 가장 널리 쓰이는 새니타이저이다. **객체 주변에 레드존을 삽입**하고, **섀도 메모리**를 사용하여 각 바이트의 접근 가능 여부를 기록한다. 1만 건이 넘는 메모리 안전성 위반을 탐지하였다.

![그림 1. ASan은 매 접근 전에 섀도 메모리를 확인하며, 레드존에 닿으면 버그를 보고함](../images/L10_p08.png)

*그림 1. ASan은 매 접근 전에 섀도 메모리를 확인하며, 레드존에 닿으면 버그를 보고함*

주소 `p`에 접근하기 전에 ASan은 섀도 메모리에서 `IsAccessible(p)`를 확인한다. 객체는 접근 불가능으로 표시된 **레드존**으로 둘러싸이므로, 범위를 벗어난 접근은 레드존에 떨어져 **버그**로 보고된다.

### 2.3 메타데이터 인코딩

아이디어는 **각 워드의 접근 가능 상태**를 섀도 메모리에 저장하는 것이다.

- 8바이트의 접근 가능 여부를 임의의 비트맵으로 표현하면 256가지 패턴이 있지만, ASan은 아래의 접두 구간 형태만 사용한다.
- **8바이트 정렬 워드**는 **9가지 상태**만 가진다: 0개부터 8개까지의 바이트가 접근 가능할 수 있다.
- 접근 가능한 바이트는 8바이트 블록의 앞부분에 연속해서 놓인다. **섀도 값 0은 8바이트 전체 접근 가능**, **1부터 7은 앞의 해당 바이트 수만 접근 가능**, **부호 있는 음수 값은 접근 불가능한 블록**을 뜻한다. 0을 접근 가능한 바이트가 0개라는 뜻으로 읽으면 안 된다.

![그림 2. ASan은 전체 주소 공간에서 매핑된 섀도 영역을 예약함](../images/L10_p15.png)

*그림 2. ASan은 전체 주소 공간에서 매핑된 섀도 영역을 예약함*

ASan은 실제 주소를 시프트와 덧셈으로 섀도 주소에 매핑한다.

```
shadow = (addr >> 3) + shadowbase
```

여기서 `shadow`는 섀도 메타데이터 테이블의 주소, `addr`은 원래 주소, `shadowbase`는 섀도 테이블의 기준 주소이다. 섀도 바이트 하나가 애플리케이션 8바이트를 덮으므로, 섀도 영역은 주소 공간의 8분의 1이며, 애플리케이션 메모리와 섀도 사이의 영역은 접근 불가능한 "Bad" 간격으로 남는다.

### 2.4 계측

**전체 워드 접근:** 모든 로드/스토어 앞에 섀도 검사가 들어간다.

```c
long getData(long *addr) {
  return *addr;
}
// becomes:
long getData(long *addr) {
  uintptr_t a = (uintptr_t)addr;
  signed char *shadow = (signed char *)((a >> 3) + shadowbase);
  if (*shadow)
    ReportError(addr);
  return *addr;
}
```

**부분(N바이트) 접근:** 8바이트보다 적게 접근하면, 마지막 접근 바이트를 섀도 값과도 비교한다.

```c
// N-byte access instead:
int last = (int)(addr & 7) + N - 1;
if (*shadow != 0 && (int)*shadow <= last)
  ReportError(addr);
```

> **의사코드의 조건:** 부분 접근 검사에서 `addr`은 정수 주소이고, `shadow`는 부호 있는 1바이트 값을 가리키며, 접근은 하나의 8바이트 블록 안에 머문다고 가정한다. 정렬된 8바이트 접근은 섀도 값 0일 때만 허용한다. 정렬되지 않은 접근이 블록 경계를 넘으면 추가 섀도 검사도 필요하며, 엔트리 하나로 모든 바이트를 판단할 수 없다.

**스택:** 스택의 객체 주변에 레드존을 삽입하고 스택 프레임에 진입할 때 오염시킨다. 함수가 실행될 때마다 레드존은 프롤로그에서 초기화되고 에필로그에서 제거된다.

**전역:** 각 전역 객체 뒤에 레드존을 삽입하고 초기화 시 오염시킨다. 예를 들어 `int original;`을 `struct { int original; char redzone[60]; } a;`(32바이트 정렬)로 바꾼다.

### 2.5 런타임 라이브러리와 보고

ASan 런타임 라이브러리는 다음을 한다.

- 시작 시 섀도 맵을 초기화한다.
- `malloc`/`free`를 대체하여 메타데이터를 갱신한다(그리고 할당에 레드존을 덧붙인다).
- `memset` 같은 특수 함수를 가로챈다.

원소가 16개인 `global_array`에서 `global_array[16]`을 읽는 프로그램에 대해, ASan은 불법 읽기의 정확한 위치와 할당 지점과 함께 **global-buffer-overflow**를 보고한다.

### 2.6 요약

AddressSanitizer는 객체 주변에 레드존을 배치하고 유발 이벤트 시 이를 검사하여 메모리 오류를 탐지한다. 탐지 대상은 다음과 같다.

- 힙, 스택, 전역에 대한 범위 밖 접근
- Use-After-Free, Use-After-Return, Use-After-Scope
- Double Free, 잘못된 free
- 메모리 누수

대표적인 측정에서 ASan의 총 실행 시간은 약 **2배**, 총 메모리 사용량은 **1.5배부터 3배**이다. 이는 추가 백분율이나 모든 프로그램에서의 보장 수치가 아니다. 메모리 누수 탐지는 LSan과의 통합 및 빌드와 실행 설정에 따라 제공된다.

ASan의 초기 적용 사례에서는 Chrome에서 3년 동안 3,000개 이상, Google 서버 소프트웨어에서 3,000개 이상, 오픈소스 소프트웨어에서 1,000개 이상의 버그가 발견되었다.

## 3. 그 밖의 새니타이저

### 3.1 LeakSanitizer (LSan)

LeakSanitizer는 **런타임 메모리 누수**를 탐지한다. AddressSanitizer와 결합하거나 단독으로 사용할 수 있다. 프로세스 종료 시 추가 누수 탐지 단계가 실행되기 전까지는 성능 오버헤드가 거의 없다. 할당된 힙 객체와 도달 가능성을 조사한 뒤 누수와 해당 할당 지점을 보고한다. 종료 시 할당 상태인 객체가 모두 누수로 보고되는 것은 아니다. [LSan 설계 설명](https://github.com/google/sanitizers/wiki/AddressSanitizerLeakSanitizerDesignDocument)을 참고한다.

### 3.2 ThreadSanitizer (TSan)

여러 스레드가 주소 공간을 공유하므로, 같은 메모리 위치의 충돌하는 접근에는 순서 보장이 필요하다. 서로 다른 스레드의 접근 중 적어도 하나가 쓰기이고 적어도 하나가 비원자적이며, happens-before 관계로 순서화되지 않으면 **데이터 경쟁(data race)** 이 발생한다. 데이터 경쟁은 C/C++에서 **정의되지 않은 동작**이다. 원자적 접근만 사용하더라도 프로그램의 더 큰 논리적 경쟁까지 모두 해결되는 것은 아니다.

![그림 3. 데이터 경쟁: 두 스레드가 동기화 없이 공유 Y를 읽고 씀](../images/L10_p29.png)

*그림 3. 데이터 경쟁: 두 스레드가 동기화 없이 공유 Y를 읽고 씀*

그림에서 Thread 1은 `Y = 5`를 읽고 `5 + 1`을 계산하는 동안, Thread 2는 같은 `5`를 읽고 `5 x 2`를 계산한다. 읽기와 쓰기 사이의 컨텍스트 스위치 때문에 두 스레드의 갱신이 뒤섞여, `Y`의 최종 값이 타이밍에 따라 달라진다(잘 정의된 결과 대신 10 다음 6).

**TSan**은 스레드 간 데이터 경쟁을 탐지한다. **로드와 스토어**, 원자적 연산, 관련 동기화 연산을 계측한다. RAW와 WAR 경쟁을 판단하려면 쓰기뿐 아니라 읽기도 기록해야 한다.

- **메타데이터:** 각 8바이트 워드는 마지막 {2, 4, 8}개의 접근을 저장하는 섀도 영역에 매핑된다. 각 접근은 16비트 스레드 ID, 42비트 에포크(스칼라 시계), 2비트 접근 크기, 3비트 접근 오프셋, 쓰기 여부 1비트를 기록한다. ASan과 비슷하게 매핑된다.
- **정책:** 모든 접근을 계측하고 메타데이터를 검사한다. 검사는 비교적 빠르지만, 메모리 오버헤드가 막대하고(5배~8배) 여전히 느리다(4배~10배).

> **용어 정의:** **WAW, RAW, WAR** 는 write-after-write, read-after-write, write-after-read로, 같은 위치에 대한 동기화되지 않은 접근 쌍 중 적어도 하나가 쓰기인 경우이다. 에포크는 스레드별 **스칼라(논리) 시계**로, TSan이 접근을 순서화하고 happens-before 관계가 있는지 판단하게 해 준다. 그런 관계가 없으면 두 접근은 경쟁한다.

> **직관:** 뮤텍스는 *happens-before* 관계의 간단한 예다. 한 스레드가 공유 데이터를 수정한 뒤 뮤텍스를 해제하고, 다른 스레드가 데이터를 읽기 전에 뮤텍스를 획득하면 두 작업의 순서가 보장된다. 이런 동기화 관계가 없으면 겹치는 읽기와 쓰기가 데이터 경쟁을 일으킬 수 있으며, TSan은 이처럼 순서 보장이 빠진 경우를 검사한다.

### 3.3 MemorySanitizer (MSan)

MemorySanitizer는 **초기화되지 않은 읽기**, 즉 초기화되지 않은 데이터를 읽는 것을 찾는다.

- **메타데이터:** MSan은 대응하는 비트 폭의 섀도 값으로 비트별 초기화 상태를 추적한다. 원인 추적 메타데이터를 제외하면 애플리케이션 1바이트당 섀도 1바이트에 해당한다. [MSan 구현](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Transforms/Instrumentation/MemorySanitizer.cpp)을 참고한다.
- **계측:** 새로 할당된 초기화되지 않은 데이터를 오염으로 표시하고, 복사와 연산을 따라 초기화 상태를 전파하며, 조건 분기나 포인터 역참조 같은 사용 지점에서 검사한다. 쓰는 값이 초기화되어 있을 때 해당 오염이 해제된다. 초기화되지 않은 데이터의 단순 복사가 즉시 보고로 이어지는 것은 아니다. [MSan 설명](https://github.com/google/sanitizers/wiki/MemorySanitizer)을 참고한다.
- 일반적인 속도 저하는 **2.5배~4배**, 메모리 오버헤드는 2배~3배이다.

> **참고:** MemorySanitizer(초기화되지 않은 읽기)와 AddressSanitizer(범위 밖 접근, Use-After-Free)를 혼동하지 않는다. 둘은 서로 다른 버그 범주를 대상으로 하며 일반적으로 동시에 활성화할 수 없다.

### 3.4 HexType

HexType은 **타입 캐스트 위반**(타입 혼동)을 찾는다.

- **구현:** 모든 캐스트(static cast, dynamic cast, placement new, C 스타일 캐스트)와 `new` 연산을 계측하는 clang 확장이며, 런타임 모듈이 기록과 명시적 캐스트 검사를 수행한다.
- 할당된 객체의 **실제 타입**을 기록하고 모든 타입 캐스트를 명시적으로 만든다.
- 대표적인 실행 시간 오버헤드는 약 **50%**, 즉 **총 실행 시간은 약 1.5배**이다.

### 3.5 UndefinedBehaviorSanitizer (UBSan)

UBSan은 C/C++ 프로그램의 전형적인 정의되지 않은 동작에서 트랩하도록 코드를 계측하여 **정의되지 않은 동작**을 탐지한다. 예는 다음과 같다.

- 잘못 정렬된 포인터의 역참조
- 부호 있는 정수 오버플로우
- 오버플로우를 일으키는 부동소수점 변환
- NULL 포인터의 불법 사용
- 불법 포인터 연산

속도 저하는 검사의 양과 빈도에 따라 다르다. UBSan의 **최소 런타임**은 운영 환경에서 공격 표면과 진단 비용을 줄이기 위한 선택지이다. GWP-ASan처럼 일부 할당을 검사하는 표본 탐지기도 운영 환경에 사용된다. 각 방식은 비용과 탐지 범위 사이에서 서로 다른 절충을 한다. 부호 없는 정수의 모듈러 오버플로우 자체는 정의되지 않은 동작이 아니다.

### 3.6 Valgrind Memcheck

Valgrind는 메모리 디버깅, 누수 탐지, 프로파일링 도구이다. 컴파일러 기반 새니타이저와 달리, **이진 변환(binary translation)** 으로 프로그램을 상위 수준 표현으로 들어 올린 뒤 그 위에 검사를 계측하므로 **재컴파일이 필요 없다**.

- Valgrind **memcheck**는 메모리 오류를 찾는다: 초기화되지 않은 메모리 사용, Use-After-Free, `malloc`된 데이터의 버퍼 오버플로우.
- 일반적인 속도 저하는 **20배~30배**이다.

> **핵심:** 컴파일러 기반 새니타이저(ASan, TSan, MSan 등)는 소스 코드와 재컴파일이 필요하지만 훨씬 빠른 반면, Valgrind는 수정되지 않은 바이너리에서 동작하지만 한 자릿수 더 느리다. 다시 빌드할 수 있는 개발 중에는 컴파일러 새니타이저를, 바이너리만 있을 때는 Valgrind를 사용한다.

## 개념 적용

**ASan 계산과 빈칸 연습:** 접근이 하나의 8바이트 블록 안에 머무르고, `s`가 부호 있는 섀도 값이라고 가정한다.

```c
shadow_addr = (addr >> ____) + shadowbase;       // A
int last = (int)(addr & ____) + N - 1;           // B
if (s != 0 && s <= ____)                        // C
  ReportError(addr);
```

> **정답:** A는 `3`, B는 `7`, C는 `last`이다. `addr & 7`은 블록 내 시작 오프셋이며, `last`는 마지막 접근 바이트의 오프셋이다. 섀도 값이 양수 `k`이면 마지막 오프셋이 `k`보다 작아야 한다. 음수 섀도 값도 오류로 판단되도록 부호를 유지해야 한다.

| 섀도 값 | 블록 내 시작 오프셋과 접근 크기 | 판단 |
|:--------|:-------------------------------|:-----|
| 0 | 오프셋 0에서 8바이트 | 허용. 전체 블록에 접근할 수 있다. |
| 5 | 오프셋 3에서 2바이트 | 허용. 마지막 오프셋 4가 5보다 작다. |
| 5 | 오프셋 4에서 2바이트 | 오류. 마지막 오프셋 5는 접근 가능한 접두 구간 밖이다. |
| 음수 | 오프셋 0에서 1바이트 | 오류. 오염된 블록이다. |

**새니타이저 선택과 한계:**

| 상황 | 선택과 설명 |
|:-----|:------------|
| 버퍼 경계를 넘거나 해제된 영역을 접근한다. | **ASan.** 접근 불가능으로 표시된 영역을 탐지한다. 모든 공간적 및 시간적 오류를 증명하는 것은 아니다. |
| 초기화되지 않은 값으로 조건을 판단한다. | **MSan.** 주소가 접근 가능해도 값이 초기화되지 않았을 수 있다. |
| 서로 다른 스레드가 순서 보장 없이 읽고 쓴다. | **TSan.** 읽기와 쓰기 및 동기화 관계를 추적한다. |
| 실제 객체와 호환되지 않는 클래스로 캐스트한다. | **HexType.** 실제 타입 메타데이터와 타입 관계를 검사한다. |
| 부호 있는 정수 오버플로우가 발생한다. | **UBSan.** 해당 정의되지 않은 동작을 계측한다. |
| 종료 시 회수되지 않은 할당을 찾는다. | **LSan.** 단순히 할당 목록의 모든 객체를 누수라고 판정하는 것은 아니며, 도달 가능성도 고려한다. |
| 다시 컴파일할 수 없는 바이너리를 검사한다. | **Valgrind Memcheck.** 이진 변환으로 계측하며 비용이 크다. |

**검사 조합과 실행 환경:** ASan과 UBSan 계열 검사를 함께 활성화하면 주소 오류와 정의되지 않은 연산을 같은 실행에서 검사할 수 있다. 오류 메시지의 종류를 보고 주소 오류인지 정의되지 않은 연산인지 구분한다. 일반 실행에서 비정상 종료하지 않았다는 사실과 새니타이저가 오류를 보고하지 않았다는 사실은 모두 버그 부재의 증명이 아니다.

예를 들어 널 인자에 대해 SIGSEGV를 기대하는 테스트는 일반 바이너리와 새니타이저 바이너리에서 결과가 다를 수 있다. 새니타이저가 신호 이전에 종료하면 Check가 기대한 신호를 받지 못한다. `CK_FORK=no`에서 같은 신호가 발생하면 테스트 전체 프로세스가 종료될 수도 있다. 도구가 바꾼 실행 환경과 프로그램의 명세를 함께 해석해야 한다.

**T/F 점검:**

| 문장 | 판단과 근거 |
|:-----|:------------|
| ASan의 섀도 값 0은 해당 8바이트가 모두 접근 불가능하다는 뜻이다. | **F.** 8바이트 전체 접근 가능을 뜻한다. |
| ASan은 모든 초기화되지 않은 읽기를 탐지한다. | **F.** 초기화 상태는 MSan의 주된 대상이다. |
| ASan의 8바이트당 1바이트 메타데이터는 프로세스 전체 메모리 사용량이 반드시 12.5%만 증가한다는 뜻이다. | **F.** 레드존, 할당기, 격리 영역 등의 비용이 추가된다. |
| 새니타이저를 붙이면 버그를 유발할 입력 생성은 필요 없다. | **F.** 탐지와 입력 탐색은 별도의 구성 요소이다. |

## 요약

| 새니타이저 | 찾는 것 | 메타데이터 | 일반적인 속도 저하 |
|:----------|:------|:---------|:-----------------|
| **ASan** (AddressSanitizer) | 범위 밖, UAF/UAR/UAS, Double/잘못된 free, 누수 | 섀도 메모리(8바이트당 1바이트) + 레드존 | 2배 |
| **LSan** (LeakSanitizer) | 메모리 누수 | 할당 객체 추적 | 종료 전까지 거의 없음 |
| **TSan** (ThreadSanitizer) | 데이터 경쟁(WAW, RAW, WAR) | 마지막 접근을 담는 섀도 영역(스레드 ID, 에포크) | 4배~10배 |
| **MSan** (MemorySanitizer) | 초기화되지 않은 읽기 | 비트별 초기화 섀도, 바이트당 1바이트 | 2.5배~4배 |
| **HexType** | 타입 혼동 | 할당 객체의 실제 타입 | 약 1.5배 |
| **UBSan** (UndefinedBehaviorSanitizer) | 정의되지 않은 동작 | 인라인 검사 | 경우에 따라 다름(운영 가능) |
| **Valgrind memcheck** | 메모리 오류(바이너리, 재컴파일 불필요) | 이진 변환 | 20배~30배 |

- 소프트웨어 테스트는 공격자가 익스플로잇하기 전에 버그를 찾는다.
- 새니타이저는 예외 발생 시뿐 아니라 **버그를 조기에 탐지**할 수 있게 하며, 용도마다 다른 새니타이저가 있다.
- ASan은 모든 할당 객체의 메타데이터를 기록하고 모든 읽기/쓰기를 검사하여 확률적 메모리 안전성을 강제한다. MSan은 초기화되지 않은 데이터를, TSan은 데이터 경쟁을, HexType은 타입 혼동을 대상으로 한다.
- **핵심 교훈: 코드를 테스트할 때 새니타이저를 사용하라.**

## 점검 문제

1. **두 구성 요소:** 동적 결함 탐지의 두 구성 요소는 무엇이며, 새니타이저의 역할은 무엇인가?

   > **정답:** 결함을 유발하는 메커니즘(퍼징과 심볼릭 실행의 역할)과 결함을 탐지 가능하게 만드는 메커니즘이 필요하다. 새니타이저는 후자에 해당하며, 실행 중 결함이 유발될 때 이를 탐지한다.

2. **섀도 메모리:** ASan은 섀도 메모리와 레드존으로 범위 밖 접근을 어떻게 탐지하는가?

   > **정답:** ASan은 모든 객체를 레드존으로 둘러싸고, 이를 별도의 섀도 메모리 영역에서 접근 불가능으로 표시한다. 섀도 바이트 하나가 애플리케이션 8바이트의 접근 가능 상태를 기록한다. 매 접근 전에 계측 코드가 섀도 주소(`(addr>>3) + shadowbase`)를 계산해 검사하며, 접근이 레드존(또는 해제된 메모리)에 떨어지면 섀도가 접근 불가능으로 표시하여 ASan이 버그를 보고한다.

3. **메타데이터 인코딩:** 8바이트 워드가 왜 9가지 상태만 가지며, 이를 어떻게 인코딩하는가?

   > **정답:** 접근 가능한 바이트가 앞부분에 연속한다고 가정하면 0개, 1개부터 7개, 8개 전체라는 아홉 상태가 있다. 각각 음수 오염 값, 1부터 7, 0으로 인코딩한다. 섀도 바이트 하나가 애플리케이션 8바이트를 표현한다. 이는 상태 표현과 검사 방식에 대한 선택이며, 1바이트가 8비트 비트맵보다 공간이 작다는 뜻은 아니다.

4. **ASan 버그 범주:** ASan이 탐지하는 버그 범주 네 가지를 말하고, 일반적인 속도 저하를 말하라.

   > **정답:** 범위 밖 접근(힙, 스택, 전역), Use-After-Free(및 Use-After-Return, Use-After-Scope), Double Free나 잘못된 free, 메모리 누수이다. 일반적인 속도 저하는 약 2배이다.

5. **TSan:** 데이터 경쟁이란 무엇이며, ThreadSanitizer는 이를 어떻게 탐지하는가?

   > **정답:** 데이터 경쟁은 서로 다른 스레드의 충돌하는 접근 중 적어도 하나가 쓰기이고 필요한 동기화 순서가 없는 경우이다. 원자적 접근은 구분해야 한다. TSan은 읽기와 쓰기에 스레드 및 시계 메타데이터를 기록하고 동기화를 관찰하여 happens-before 관계가 없는 충돌을 찾는다. 스칼라 에포크 하나만으로 전체 동기화 모델이 구성되는 것은 아니다.

6. **새니타이저 선택:** 초기화되지 않은 읽기를 대상으로 하는 것, 타입 혼동을 대상으로 하는 것, 운영 환경에서 실행할 수 있는 것은 각각 무엇인가?

   > **정답:** MSan은 초기화되지 않은 읽기를, HexType은 타입 혼동을 대상으로 한다. UBSan 최소 런타임과 GWP-ASan 같은 표본 탐지기는 운영 환경에서 사용할 수 있다. 표본 탐지기는 일부 할당만 검사하여 탐지 범위와 비용을 조절한다.

7. **Valgrind vs 컴파일러 새니타이저:** Valgrind는 컴파일러 기반 새니타이저와 어떻게 다르며, 트레이드오프는 무엇인가?

   > **정답:** Valgrind는 이진 변환으로 수정되지 않은 바이너리를 계측하므로 소스 코드나 재컴파일이 필요 없는 반면, 컴파일러 기반 새니타이저는 `-fsanitize=address` 같은 플래그로 재컴파일해야 한다. 트레이드오프는 속도이다. Valgrind는 약 20배~30배 느린 반면 ASan은 약 2배이므로, 개발 중에는 컴파일러 새니타이저를, 바이너리만 있을 때는 Valgrind를 선호한다.
