## 1. 제어 흐름 탈취에 대한 고급 완화 기법

- 제어 흐름 탈취는 공격자에게 **가장 높은 유연성**을 준다.
- 배포된 완화 기법(ASLR, DEP, 스택 카나리)은 제어 흐름 탈취를 **더 어렵게 만들 뿐, 불가능하게 만들지는 않는다**.
- **목표:** 고급 보호 기법으로 제어 흐름 탈취를 더욱 제한한다.

### 1.1 제어 흐름 탈취의 요구 조건

제어 흐름을 탈취하려면 공격자는 다음을 해야 한다.

1. **코드 포인터를 덮어쓴다**
2. **알려진 값으로**
3. 수정된 코드 포인터의 **사용을 유발한다**

**고급 완화 기법은 수정된 코드 포인터의 사용을 제한한다.**

> **[컴퓨터구조]** 코드 포인터는 프로세서가 다음 명령어 위치로 사용할 수 있는 주소를 저장한다. 함수 반환은 저장된 복귀 주소를 사용하고, 간접 호출이나 점프는 함수 포인터와 같은 값을 사용한다. 이들이 스택 무결성과 CFI가 보호하는 후방 및 전방 제어 흐름 간선이다.

### 1.2 제어 흐름 탈취의 목표

코드 포인터에는 네 가지 유형이 있다.

| 코드 포인터 | 어셈블리 |
|:-------------|:---------|
| 함수 복귀(return) | `return` |
| switch 문 | 간접 점프 |
| 함수 포인터 | 간접 호출 |
| 가상 디스패치 | 간접 호출 |

### 1.3 방어의 현재 상태

- DEP가 있으므로 공격자는 **코드 포인터를 덮어써야** 한다.
- **간접 점프는 목표가 아니다:**
  - switch 문은 (컴파일러가) 경계 검사한다.
  - 로더 자료 구조의 점프는 쓰기 보호된다.
- **복귀**가 고전적인 목표이고, **간접 호출**이 대안이다.
- 스택 카나리 때문에 복귀는 익스플로잇하기 어려워져, (확정적이지는 않지만) 간접 호출로의 패러다임 전환이 있다.

### 1.4 개요

고급 완화 기법은 남은 두 범주를 목표로 한다.

| 완화 기법 | 보호 대상 |
|:-----------|:---------|
| **스택 무결성** | 복귀(backward edge) |
| **제어 흐름 무결성(CFI)** | 간접 호출(forward edge) |
| **코드 포인터 무결성(CPI)** | 간접 호출(및 모든 코드 포인터) |

> **용어 정의:** 제어 흐름 그래프에서 **backward edge(후방 간선)** 는 함수에서 호출자로의 복귀이고, **forward edge(전방 간선)** 는 피호출자로의 간접 호출이나 점프이다. 스택 무결성은 후방 간선을 보호하고, CFI와 CPI는 전방 간선에 초점을 맞춘다.

## 2. 스택 무결성

### 2.1 정의

**스택 무결성(stack integrity)** 은 (i) **복귀 명령 포인터**와 (ii) **스택 포인터**가 수정될 수 없음을 보장한다.

- 복귀 명령 포인터는 코드 포인터이며, 스택 무결성은 유효한 복귀 명령 포인터만 역참조됨을 보장한다.
- 다른 스택 프레임을 가리키는 포인터는 스택에 저장되며, 스택 무결성은 이 메타데이터의 무결성을 보장한다. 베이스 포인터를 수정하면 복귀 명령 포인터도 간접적으로 수정된다는 점에 유의한다.

| 형태 | 강도 |
|:-----|:---------|
| 스택 카나리 | 약한 형태의 스택 무결성 |
| 섀도 스택 | 강한 형태의 스택 무결성 |
| 세이프 스택 | 부분적 데이터 보호를 갖춘 강한 형태 |
| 메모리 안전성 | (부수 효과로) 완전한 스택 무결성 |

### 2.2 섀도 스택

**섀도 스택(shadow stack)** 은 각 스레드마다 제어 데이터(예: 복귀 명령 포인터, 베이스 포인터)를 추적하는 두 번째 스택이다.

![그림 1. 섀도 스택이 메인 스택의 복귀 주소를 복제함 (슬라이드 14)](../images/L08_p14.png)

*그림 1. 섀도 스택이 메인 스택의 복귀 주소를 복제함 (슬라이드 14)*

- 모든 구현이 모든 유형의 데이터를 보호하는 것은 아니다.
- 섀도 스택의 데이터는 **무결성이 보호된다**:
  - **암묵적으로:** 섀도 스택은 제어 데이터만 담으므로 버퍼 오버플로우가 불가능하다.
  - **명시적으로:** 일부 섀도 스택은 쓰기 보호된다.
- **한계:** 데이터 손상은 잡지 못한다(제어 데이터만 보호됨).

> **[컴퓨터구조]** 호출 시 복귀 주소를 일반 스택과 섀도 스택 양쪽에 푸시한다. 복귀 시 두 사본을 비교하여 다르면 프로그램을 중단한다. Intel CET는 이를 하드웨어(`SHSTK`)로 제공하여 오버헤드가 거의 없는 반면, 소프트웨어 섀도 스택은 모든 호출과 복귀에 명령을 추가한다.

### 2.3 세이프 스택

**세이프 스택(safe stack)** 은 각 함수의 프레임을 안전한 부분과 안전하지 않은 부분으로 나눈다.

![그림 2. 안전한 변수는 세이프 스택에, 오버플로우 가능한 버퍼는 일반 스택에 둠 (슬라이드 16)](../images/L08_p16.png)

*그림 2. 안전한 변수는 세이프 스택에, 오버플로우 가능한 버퍼는 일반 스택에 둠 (슬라이드 16)*

- 핵심 아이디어는 **스택 프레임의 각 변수가 안전한지 판단**하는 것이다.
- 변수는 안전한 맥락에서만 사용되면, 즉 현재 함수를 벗어나지 않고(escape하지 않고) 경계가 있는 포인터 연산에만 사용되면 **안전**하다.
- **안전하지 않은 변수**(예: 오버플로우 가능한 버퍼)는 **안전하지 않은 스택**으로 밀어 넣는다.
- **성능 이점:** 안전하지 않은 변수가 있을 때만 안전하지 않은 스택 프레임이 할당된다.
- **한계:** 안전하지 않은 데이터의 손상은 잡지 못한다.

`int foo() { char buf[16]; int r; r = scanf("%s", buf); return r; }` 예제에서, 복귀값 `r`과 복귀 주소는 세이프 스택에 남고 오버플로우 가능한 `buf`는 일반 스택으로 가므로, `buf`의 오버플로우가 복귀 주소에 도달할 수 없다.

### 2.4 스택 무결성 요약

| 메커니즘 | CF 탈취 방어 | 데이터 보호 | 오버헤드 |
|:----------|:-----------------------------:|:-------------:|:---------|
| 스택 카나리 | 연속적인 오버플로우만 | 없음 | 무시할 수준 |
| SW 섀도 스택 | 가능 | 없음(데이터 손상 허용) | 높음 |
| HW 섀도 스택 | 가능 | 없음(데이터 손상 허용) | 무시할 수준 |
| 세이프 스택 | 가능 | 안전한 데이터만 | 낮음 |

## 3. 제어 흐름 무결성 (CFI)

### 3.1 정의

**CFI**는 애플리케이션을 제어 흐름 탈취 공격으로부터 보호하는 방어 메커니즘이다. 성공적인 CFI 메커니즘은 애플리케이션의 제어 흐름이 소스 코드나 애플리케이션 수준에서 정의된 **미리 정해진 유효한 제어 흐름을 결코 벗어나지 않음**을 보장한다. 즉, 공격자가 제어 흐름을 대체 위치나 새로운 위치로 돌릴 수 없다.

**핵심 아이디어:** 애플리케이션의 동적 제어 흐름을 애플리케이션의 **제어 흐름 그래프**로 제한한다. 이를 위해 다음이 필요하다.

1. **목표 집합 구성(target set construction)**
2. 런타임 검사를 실행하는 **동적 강제 메커니즘**

### 3.2 목표 집합 구성

C/C++ 프로그램의 제어 흐름 그래프를 어떻게 추론하는가? **정적 분석**(소스 코드나 바이너리에 대한)으로 제어 흐름 그래프의 **근사치**를 복구할 수 있다. **분석의 정밀도가 핵심이다.**

- **정밀도와 호환성** 사이에 트레이드오프가 있다.
- 유효한 함수들의 단일 집합 하나는 다른 소프트웨어와 호환성이 높지만, 함수가 매우 많으면 **부정확**할 수 있다.

### 3.3 런타임 검사

분석은 간접 제어 흐름 전환의 각 위치에 대한 **목표 집합**을 생성한다. 런타임 검사는 런타임 값과 목표 집합을 이용해 **집합 검사(set check)** 를 수행한다. 가장 효율적인 구현은 비트 마스크 집합을 사용한다.

```c
void (*fn)(int) = &func;
...
if (!contains(targetset, fn)) {
  abort("Error: illegal target");
}
fn(12);
```

검사와 디스패치는 **원자적(atomic)** 이어야 한다. 그렇지 않으면 공격자가 검사와 호출 사이에 포인터를 바꿀 수 있어 **TOCTTOU** 취약점이 된다.

### 3.4 한계와 요약

**한계:**

- CFI는 **근본 버그가 발생하도록 허용**하며, 메모리 손상은 공격자가 제어할 수 있다. 방어는 손상된 포인터가 사용될 때 비로소, 즉 **사후에** 일탈을 탐지한다.
- 정적 분석의 **과근사(over-approximation)** 는 보안을 약화시킨다(목표 집합이 클수록 더 많은 불법 목표가 통과한다).

**요약:**

- CFI는 **전방 간선**을 보호하는 고급 완화 기법이다.
- 컴파일러가 호출별 목표 집합을 정적으로 추론한다.
- 런타임에 집합 검사로 관찰된 목표가 유효한지 보장한다.
- 런타임 오버헤드는 **낮으며, 보통 2% 미만**이다.
- **스택 무결성을 전제로** 보안이 좋다(CFI 단독으로는 복귀를 보호하지 않는다).
- 공격을 훨씬 어렵게 만든다.

## 4. 코드 포인터 무결성 (CPI)

### 4.1 동기

- 메모리 손상은 흔하다.
- 강한 메모리 안전성 기반 방어는 **채택되지 않았다**.
- 강한 메모리 할당기 같은 약한 방어도 외면받았다.
- **무시할 수준의 오버헤드**를 가진 방어만 채택된다.
- **정말 중요한 곳에만 메모리 안전성을 적용할 수 있다면?**
- **코드 포인터 무결성(CPI)** 은 모든 코드 포인터가 항상 보호됨을 보장한다.

**CPI 공격자 모델:**

- 공격자는 데이터와 코드(스택, bss, data, text, heap)를 **읽을** 수 있다.
- 공격자는 데이터를 **쓸** 수 있다.
- 공격자는 **코드를 수정할 수 없다**.

기존 메모리 안전성 솔루션의 오버헤드가 문제다: SoftBound+CETS 116%, CCured 56%, AddressSanitizer 73%(그리고 부분적 메모리 안전성만 제공).

### 4.2 조금만, 완전하게 보호

**모든 것을 조금씩 보호하는 대신, 조금만 완전하게 보호한다:** 선택된 데이터 부분집합에 강한 보호를 제공한다.

- 공격자는 **보호되지 않은** 데이터는 수정할 수 있다.
- **코드 포인터만** 보호함으로써, CPI는 메모리 안전성의 오버헤드를 **116%에서 8.4%로** 줄인다.
- CPI는 제어 흐름 탈취를 **결정적으로** 방어한다.

### 4.3 무엇을 보호해야 하는가

- **민감한 포인터(sensitive pointer)** 는 코드 포인터와 민감한 포인터에 접근하는 데 사용되는 포인터이다.
- **타입**을 통해 민감한 포인터를 **과근사**하여 식별할 수 있다: 민감한 포인터의 모든 타입은 민감하다.
- 과근사는 보안이 아니라 성능에만 영향을 준다.

![그림 3. 민감한 포인터는 타입을 통해 전이적으로 식별됨 (슬라이드 31)](../images/L08_p31.png)

*그림 3. 민감한 포인터는 타입을 통해 전이적으로 식별됨 (슬라이드 31)*

그림에서, 함수 포인터를 포함하는 구조체는 민감하고, 그 구조체를 가리키는 포인터도 민감하므로, "민감" 표시가 타입 그래프를 따라 전이적으로 전파된다. 반면 일반 데이터(예: `int`)는 보호되지 않은 채 남는다.

### 4.4 메모리 레이아웃

![그림 4. 메모리가 보호된 안전 평면과 일반 평면으로 나뉨 (슬라이드 32)](../images/L08_p32.png)

*그림 4. 메모리가 보호된 안전 평면과 일반 평면으로 나뉨 (슬라이드 32)*

- 메모리 뷰는 두 가지 뷰로 나뉜다: **제어 평면(control plane)** 과 **데이터 평면(data plane)**.
  - **제어 평면**은 코드 포인터만(그리고 전이적으로 관련된 모든 포인터를) 담는다.
  - **데이터 평면**은 데이터만 담으며, 코드 포인터는 비워 둔다(void/미사용).
- 두 평면은 **분리**되어야 하며, 제어 평면의 데이터는 데이터 평면의 포인터 역참조로부터 **보호**되어야 한다.

### 4.5 요약

- CPI는 **선택된 데이터**에 메모리 안전성을 강제하여 코드 포인터와 민감한 포인터를 보호한다.
- CPI는 제어 흐름 탈취를 금지한다.
- **6%~8%** 의 오버헤드는 여전히 일반적인 배포에는 너무 높다.

## 요약

- 배포된 방어(ASLR, DEP, 스택 카나리)는 **불완전**하며 모든 공격을 막지 못한다.
- **제어 흐름 탈취**가 가장 다재다능한 공격 벡터이다.

| 고급 완화 기법 | 보호 대상 | 어셈블리 | 핵심 아이디어 |
|:--------------------|:---------|:---------|:---------|
| **스택 무결성** | 후방 간선(복귀) | `ret` | 복귀 주소를 보호(섀도 스택, 세이프 스택) |
| **CFI** | 전방 간선(간접 호출) | `call*` | 각 간접 호출을 정적으로 계산된 목표 집합으로 제한 |
| **CPI** | 모든 코드 포인터 | `call*` | 코드 포인터에만 메모리 안전성을 강제(조금만, 완전하게) |

## 점검 문제

1. **탈취 요구 조건:** 공격자가 제어 흐름을 탈취하려면 어떤 세 가지를 해야 하며, 고급 완화 기법은 무엇을 목표로 하는가?

   > **정답:** 공격자는 코드 포인터를 알려진 값으로 덮어쓰고, 수정된 코드 포인터의 사용을 유발해야 한다. 고급 완화 기법은 수정된 코드 포인터의 사용을 제한하는 데 초점을 맞춰, 손상된 포인터라도 제어 흐름을 불법 목표로 돌리는 데 쓰일 수 없게 한다.

2. **코드 포인터:** 코드 포인터의 네 가지 유형을 말하고, 간접 점프가 왜 더 이상 목표가 아닌지 설명하라.

   > **정답:** 함수 복귀, switch 문, 함수 포인터, 가상 디스패치이다. 간접 점프(switch 문)는 컴파일러가 경계 검사하고 로더 자료 구조의 점프는 쓰기 보호되므로 더 이상 목표가 아니며, 복귀와 간접 호출이 주요 목표로 남는다.

3. **섀도 스택 vs 세이프 스택:** 섀도 스택과 세이프 스택은 각각 복귀 주소를 어떻게 보호하며, 각각의 한계는 무엇인가?

   > **정답:** 섀도 스택은 복귀 주소(와 제어 데이터)의 두 번째 사본을 유지하고 복귀 시 비교하므로 변조된 복귀 주소를 탐지한다. 한계는 제어 데이터만 보호하므로 데이터 손상은 잡지 못한다는 것이다. 세이프 스택은 안전한 변수와 복귀 주소를 별도의 세이프 스택에 두고 안전하지 않은 변수(버퍼 등)를 일반 스택으로 옮기므로 오버플로우가 복귀 주소에 도달할 수 없다. 한계는 안전하지 않은 데이터의 손상은 잡지 못한다는 것이다.

4. **CFI 메커니즘:** CFI 메커니즘의 두 부분은 무엇이며, 검사와 디스패치는 왜 원자적이어야 하는가?

   > **정답:** CFI는 목표 집합 구성(정적 분석으로 근사 제어 흐름 그래프와 각 간접 전환의 목표 집합을 복구)과 동적 강제 메커니즘(런타임 집합 검사)으로 이루어진다. 검사와 디스패치가 원자적이지 않으면 공격자가 검사와 호출 사이에 코드 포인터를 바꿀 수 있으며, 이것이 TOCTTOU 취약점이다.

5. **CFI 한계:** CFI는 왜 근본 버그를 막지 못하며, 분석 정밀도는 보안에 어떤 영향을 주는가?

   > **정답:** CFI는 버그가 발생하고 메모리가 손상되도록 허용하며, 손상된 포인터가 간접 전환에 사용될 때 비로소 일탈을 탐지한다. 정적 분석이 목표 집합을 과근사하면 더 많은 불법 목표가 유효한 것으로 간주되므로, 정밀도가 낮은 분석은 더 약한 보안을 제공한다.

6. **CPI 패러다임:** "조금만, 완전하게 보호" 아이디어는 무엇이며, CPI는 무엇을 보호할지 어떻게 결정하는가?

   > **정답:** 모든 데이터를 약하게 보호하는 대신, 작고 선택된 부분집합인 코드 포인터와 그에 도달하는 데 쓰이는 민감한 포인터를 강하게(완전하게) 보호한다. 이들을 타입으로 과근사하여 식별하므로 민감한 포인터 타입의 모든 값이 보호된다. 이로써 완전한 메모리 안전성의 오버헤드를 약 116%에서 약 8%로 줄이면서 제어 흐름 탈취를 결정적으로 방어한다.
